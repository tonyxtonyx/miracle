# S3 — causal, falsification-oriented diagnosis stage (design)

Status: design for the `s3-diagnosis` branch. S0/S1/S2 and checker-eval are frozen; nothing here changes their behaviour (the only touched shared
code is additive: `Task.artifact_dir`, optional `Environment` reset methods, a shared git-state helper).

## 1. What is being tested

Not solve rate or cost. The primary object is the **quality of the diagnosis**: hypotheses that are falsifiable, probes that discriminate between
them, evidence that is auditable, belief updates that follow the evidence. Official SWE-bench resolution, tokens, cost, tool calls and wall time are
recorded but are not optimisation targets and are never folded into the diagnosis-quality score.

`root cause` is generalised to **causal mechanism or implementation gap** for tasks that are not classical bugs.

## 2. Roles and context boundaries

| role | sees | may do | may not do |
|---|---|---|---|
| **Controller** (LLM, own context per call) | issue, compact repo map, graph summary, hypothesis statuses, budgets, compact evidence summaries, contradictions, unexplained observations | create/prioritise hypotheses, define falsification criteria, plan probes, select the next branch, update statuses (with a recorded cause), request synthesis, commit the diagnosis | run repository tools, free-form investigation |
| **Investigator** (LLM, one hypothesis branch, own context) | issue, **one** hypothesis + refinement chain, its predictions/falsification criteria, evidence already on the branch, competing hypotheses (compact), unresolved questions, remaining branch budget | read/search/run/edit (temporarily), record evidence and evidence→hypothesis relations through validated tools, finish with a structured report | create hypotheses, change statuses, commit; it never touches the global graph except through the evidence/relation facade |
| **Synthesis** (LLM, separate call) | compact but complete graph (no raw conversation) | create/refine/merge hypotheses, mark inconclusive | repository tools |
| **Implementation agent** (S1-style loop) | issue, committed diagnosis, selected supporting evidence, rejected alternatives, unresolved risks, compact repo map | the S0 tool set | the reasoning graph, probes, raw investigator traces |

The candidate side never receives the gold patch, test patch, `FAIL_TO_PASS`, `PASS_TO_PASS` or hints: it is built from `Task` (explicit whitelist).
Regression tests assert this both functionally (sentinel values never appear in any prompt) and statically (candidate-side modules never name those fields).

## 3. Data model (typed graph, append-only event log is the source of truth)

IDs are generated by the runtime and namespaced by instance (`django__django-11099:H3`). Prompts and tools use the short form (`H3`, `E7`, `P2`); the runtime
resolves it. Entities: **Hypothesis** (claim, type ∈ root_cause/mechanism/implementation_gap/location, parent_ids, status ∈ proposed/investigating/supported/
weakened/refuted/inconclusive/selected, predictions, falsification_criteria, ordinal support level, created/last-updated step, unresolved_questions),
**Evidence** (type, source_tool_call_id, repository state, path, line range, exact excerpt, excerpt hash, command, exit code, duration, intervention ID,
observation state `original|post_intervention`, step), **Relation** (evidence→hypothesis: supports/contradicts/explains; probe→hypothesis: tests;
hypothesis→hypothesis: refines/depends_on/alternative_to; rationale, strength 1–3), **Probe** (targets, purpose, planned action, expected outcomes, actual
evidence IDs, cost/tool-call metadata, status), **Diagnosis** (selected hypotheses, causal explanation, affected symbols, requirements explained, strongest
evidence, rejected alternatives with reasons, unresolved risks, implementation direction), plus **Branch** and **Intervention** records.

State is *derived*: `GraphState.apply(event)` is a pure function of the event, so `replay(events, upto=n)` reproduces the graph at any step (UI replay, judges).
Refuted hypotheses and contradicting evidence are never deleted.

**Integrity by construction** (the model cannot fabricate provenance):
- code evidence: the model supplies `path/start/end`; the **runtime reads the excerpt** from the repository and hashes it; paths outside the repo are rejected;
- tool-derived evidence: must reference a recorded tool call; a quoted excerpt must be an exact substring of that call's recorded output;
- issue evidence: the quote must be an exact substring of the issue text;
- a status change needs a recorded cause: `refuted/weakened` require evidence with a `contradicts` relation to that hypothesis, `supported` requires non-issue evidence
  with a `supports` relation, others require a controller decision rationale; `selected` is set only by `commit_diagnosis`; a refuted hypothesis can be reopened only with
  evidence newer than the refutation.

## 4. State machine (orchestrated in Python; the LLMs make the reasoning decisions)

```
ORIENT      deterministic repo map + issue-term hits (no free investigation)
HYPOTHESIZE controller: >=2 hypotheses, each with predictions + falsification criteria; probes that discriminate; alternative_to links
loop (bounded by iterations):
  SELECT      controller picks a hypothesis (+ probes + branch budget)         [Python fallback: highest-priority open hypothesis]
  INVESTIGATE investigator branch (isolated context, disposable state) -> evidence + relations applied by the runtime
  RESET       end interventions, restore baseline, VERIFY clean (recorded)
  REVIEW      controller: status updates (with causes), new/refined hypotheses, new probes, or commit / request synthesis
  SYNTHESIS?  Python triggers (see 5) or controller request -> dedicated synthesis call over the compact graph
COMMIT      controller commits (validated) or the budget forces an honestly-labelled inconclusive diagnosis
RESET       final restore + verification
HANDOFF     only the allowed material goes to the implementation stage
IMPLEMENT   simple S1-style loop
```

## 5. Global synthesis triggers
all active hypotheses refuted/below threshold · no open probe discriminates between the remaining hypotheses · evidence unexplained by every hypothesis (investigator-flagged) ·
evidence contradicts the current leader · equivalent actions repeated · no progress for N iterations · graph size/depth limit.

## 6. Temporary changes and reset strategy

Investigators may edit/instrument. Safe lifecycle: **verify clean baseline → (branch) first write opens an intervention with an ID → probe outputs are tagged with the
intervention ID and `observation_state=post_intervention` → branch end: end interventions, reset, verify → next branch.** One container is reused (explicit, tested
reset instead of a container per branch): `git read-tree --reset -u <baseline tree>` + `git clean -fd`, then verification = no patch-visible diff vs the baseline tree, no
unstaged/untracked non-ignored files, HEAD unchanged. A `run_command` that modifies the tree without a tool write is caught by a dirty-state check after every command (an
intervention is opened retroactively and the evidence is tagged post-intervention). Ignored files (bytecode, caches) are not part of the contract and are reported as such.
A failed verification is an infrastructure failure (existing policy), never silently ignored. After the diagnosis commit everything is reset again before implementation starts.

## 7. Judges (three layers, kept separate)

A. **Official outcome**: the existing harness; recorded separately, never mixed into the diagnosis score.
B. **Blind process judge** (Claude, isolated call): issue, cited code excerpts, graph, probes, evidence, tool trace, committed diagnosis (+ the agent's own patch for one field).
   Never: gold patch, test patch, F2P/P2P, hints, official result.
C. **Oracle judge** (Claude, two isolated calls): (1) *reference account first* from issue + base-repo excerpts + gold/test patch + F2P/P2P, **without** the candidate; it distinguishes
   established facts, inferences from the gold patch, uncertainty and alternative valid explanations, and is **persisted**; (2) only then the candidate graph/diagnosis/patch + official result are
   shown for comparison against the persisted reference (semantic, not file overlap; it also reports hindsight leakage).
Scores are 0–4 per dimension (12 dimensions; component scores are never collapsed into one number). Every finding must cite hypothesis/evidence/probe/relation IDs; citations are validated
against the graph and invalid ones trigger one repair round. Backends: official `anthropic` SDK (needs `ANTHROPIC_API_KEY`), the `claude -p` CLI (needs a login), file exchange, mock.

## 8. Web interface (read-only)
`miracle graph serve RUN [--instance ID] [--port N]`: stdlib `http.server` + plain HTML/CSS/JS, no CDN/build/DB, data read from the recorded artefacts, polling for live runs, independent of the LLM
service. Run/task selector, controller state and budgets, SVG hypothesis tree with typed cross-links and evidence nodes, status colours, expandable predictions/falsification criteria, evidence panel
(code excerpt with path/lines/revision/hash; commands with exit code/duration/output; intervention badge), chronological timeline, replay slider (graph state at any event), filters, final diagnosis and risks, judge scores.

## 9. Artefact layout (per instance, under `runs/<run>/agent/<instance>/`)
```
diagnosis/events.jsonl  graph.json  diagnosis.json  controller_trace.json  reset_verification.json  tool_calls.jsonl  repo_map.txt
diagnosis/investigators/<branch>.json
implementation/result.json  patch.diff  trace.json
judge/blind.json  reference_diagnosis.json  oracle.json  raw/*.json
report.json  report.md           (+ the standard result.json / patch.diff / trace.json used by the runner)
```
Cross-task reports are written to `runs/<run>/aggregate_report.{json,md}`.

## 10. Freezing
Prompts, config and judge rubrics live in versioned modules; `miracle diagnosis freeze` writes `FROZEN.json` (sha256 of every template, config, code commit). The run manifest records them; the
pipeline refuses to start on a mismatch. Prompts are tuned only against a toy repository, never against the target list.

## 11. Assumptions
1. The candidate model stays `Qwen/Qwen3.5-9B` via DeepInfra (separate calls for controller / investigator / synthesis, same model). Judges are Claude (`claude-opus-5-5` by default).
2. The ordered target list is supplied by the user as a file of instance IDs; it is processed in order with no skipping or substitution.
3. Evidence/relations written by an investigator go through a validating facade; hypothesis creation, status changes and the diagnosis stay controller-only.
4. A patch-visible clean baseline (not byte-identical ignored files) is the reset contract.

## 12. Risks
| risk | mitigation |
|---|---|
| a 9B model produces malformed or shallow structured output | native function calling, runtime-generated IDs with short aliases, validation errors returned as tool errors with guidance and bounded retries, Python fallbacks (default selection, honest inconclusive commit) |
| context growth / cost | controller never sees raw traces, branch budgets, compact summaries, output caps |
| over-long runs under emulated containers | iteration/branch budgets, recorded wall time; budgets are config, not tuned per task |
| reset gaps (state leaking between branches) | explicit verification after every branch, dirty check after commands, tested on a real git repo |
| judge variance / anchoring / leakage | separate calls, reference persisted before comparison, ID-citation validation, input builders with explicit allowlists + sentinel tests |
| judge availability (no Claude credentials here yet) | pluggable backends incl. file exchange; everything is unit-tested with a mock judge |
| prompt tuning against the target list | freeze + hashes in the manifest; tuning only on a toy repo |

## 13. What changed after the first real-model runs (toy task only, before the freeze)

The architecture was exercised with the real candidate model (`Qwen3.5-9B`) on the toy repository in `diagnosis/toytask` (never on SWE-bench tasks). Findings and the general,
task-independent mechanisms they led to (the tests in `tests/test_diagnosis_*.py` pin each one):

| finding with the real model | mechanism added |
|---|---|
| The controller created hypotheses one per step until the global cap (12) and never planned a probe or stopped; it narrates at length in plain text instead of following the multi-step protocol. | A planning-phase cap (`max_initial_hypotheses=5`) enforced by the tool layer, and **protocol-state reminders appended to every controller tool result** ("n hypotheses so far, limit 5; next: link alternatives, plan a discriminating probe, call done_planning"). Same fix pattern as S0's "does not stop" finding: restate the state, enforce the bound structurally. |
| Fabricated provenance was attempted (a quote that is not in the tool output) and a premature refutation was attempted. | Both were rejected by the validation layer and logged (`operation_rejected` events): the integrity-by-construction rules work against a real model. |
| To refute a duplicate hypothesis (H4 = H1), the controller linked, as `contradicts` H4, evidence the investigator had linked as `supports` H4: it satisfied the refutation gate with an incoherent relation. | The same evidence can no longer both support and contradict one hypothesis; the controller can `merge_hypotheses` during review (not only in synthesis); the review prompt says to merge rather than refute duplicates. |
| Rejections raised by the tool layer (caps, protocol rules) were returned to the model but not logged. | All rejections are logged as events, so the judges see the model's format and logic errors. |
| A buggy cleanup in the host environment once deleted the parent of a caller-supplied directory (the user's temp folder). | `HostEnvironment` deletes only a directory it created itself (marker file + prefix + direct-parent check); regression test. |

Not changed: the graph model, the state machine, the judges. After these fixes the prompts and configuration were frozen (`FROZEN.json`).
